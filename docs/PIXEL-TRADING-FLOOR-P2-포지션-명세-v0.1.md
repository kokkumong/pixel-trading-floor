## 0. 배경과 결정

사용자 결정(2026-09-30): 이 앱은 사용자 본인(과 링크를 받은 소수)이 **실제 투자 판단에 참고**하려고 쓴다. 따라서 P0 명세 결정 D3("포지션 입력을 두지 않는다")의 근거인 "개인 맞춤 조언화 회피"는 더 이상 목표가 아니다. 대신 다음을 지킨다.

- **주문 기능은 여전히 없다.** 앱은 판정만 내리고 실행은 사람이 거래소에서 한다. 거래소 API 키를 받지 않고, 자금 이동·주문 코드를 넣지 않는다 (CLAUDE.md).
- **개인 금융 정보는 최소로 다룬다.** 로컬에만 저장하고, 모델에는 비율 정보만 보낸다 (5장, 4장).
- **서비스가 아니다.** 사용자 각자가 자기 PC에서 실행하며 서버 운영·계정·결제가 없다.

### 0.1 용어

| 용어 | 뜻 |
|---|---|
| 포지션(`Position`) | 사용자가 입력한 실제 보유 1건. 현물 보유 또는 선물 롱/숏 |
| 포지션 북(`PositionBook`) | 포지션 목록 + 계좌 정보 (`.floor/positions.json`) |
| 포지션 컨텍스트(`PositionContext`) | 한 번의 분석에 쓰이는, 대상 종목의 포지션 1건(또는 없음)과 계산 결과. 작업 시작 시 고정된다 |
| 매칭 키 | `(instrumentId, marketType)`. 같은 키의 포지션만 그 분석에 쓴다 |

### 0.2 P0와 달라지는 점 요약

| 항목 | P0 | P2 |
|---|---|---|
| 포지션 입력 | 없음 | 있음 (1장) |
| 행동 | `ENTER_LONG` `ENTER_SHORT` `NO_TRADE` | + `HOLD` `ADD` `REDUCE` `EXIT` (2장) |
| `NO_TRADE` 화면 주석 | "보유 여부를 모르는 상태의 시장 방향 판단" | 포지션이 없다고 확인된 분석에서만 (6장) |
| 모델 입력 | 시장 데이터만 | 결정 역할은 포지션 **비율** 정보 추가 (4장) |
| 수량 | 없음 | 코드가 리스크 예산으로 계산한 제안 수량 (3.3절) |

## 1. 포지션 입력 (P2-1)

### 1.1 스키마

```yaml
PositionBook:
  schemaVersion: "positions/1"
  updatedAt: ISO-8601
  account:
    equity:                       # 통화별 총 자산 (선택). 예: { KRW: 30000000, USDT: 5000 }
      KRW: number | 없음
      USD: number | 없음
      USDT: number | 없음
    riskPerTradePercent: number   # 1회 손실 한도 %, 기본 1, 범위 0.1~5
  positions: Position 배열 (최대 50)

Position:
  id: UUID
  instrumentId: 문자열            # 레지스트리 ID
  marketType: spot | perpetual
  side: LONG | SHORT              # spot이면 LONG만
  avgEntryPrice: number           # 평균 진입가 (> 0)
  quantity: number                # 기초 자산 수량 (> 0). 계약 수가 아니라 코인·주식 수량
  leverage: 정수 | null           # perpetual이면 1~20, spot이면 null
  marginMode: isolated | cross | null
  liquidationPrice: number | null # 거래소 화면에 표시된 청산가. 사용자가 입력 (선택)
  stopLoss: number | null         # 현재 걸어 둔 손절 (선택)
  targets: number 배열 (0~3개)
  openedAt: ISO-8601 | null       # 선택
  note: 문자열 (최대 200자)       # 사용자 메모. 모델에 보내지 않는다 (P2-4-R2)
```

### 1.2 요구사항

- **P2-1-R1 (반드시)** 입력은 화면 폼으로 받고 파일 `.floor/positions.json`에 저장한다. 같은 스키마의 JSON 파일을 직접 편집해도 다음 읽기에서 같은 검증을 받는다.
- **P2-1-R2 (반드시)** 검증은 서버 코드가 한다: 가격·수량 양수 유한수, `spot`이면 `side = LONG`·`leverage = null`, `perpetual`이면 `leverage` 1~20 정수, 롱이면 `liquidationPrice < avgEntryPrice`·숏이면 `>`. `stopLoss`는 평단 기준 방향을 강제하지 않는다(수익권 트레일링 손절 허용). 현재가 기준 방향은 분석 시점에 검사한다(3.1절). `instrumentId`는 레지스트리에 있어야 한다. 검증 실패는 저장하지 않고 필드별 오류를 돌려준다.
- **P2-1-R3 (반드시)** 매칭 키가 같은 포지션은 1건만 둔다. **헤지(같은 종목 롱·숏 동시 보유)는 지원하지 않는다** (D21). 중복 입력은 거절한다.
- **P2-1-R4 (반드시)** 총 자산은 통화별로 따로 입력한다. 환율 환산은 하지 않는다. 대상 종목 통화의 총 자산이 없으면 수량 제안만 생략하고 나머지는 동작한다 (경고 `NO_EQUITY`).
- **P2-1-R5 (반드시)** 저장은 원자적으로 한다(임시 파일 → rename), 파일 권한은 소유자만 읽기·쓰기(0600), 직전 버전 1개를 `.floor/positions.json.bak`으로 남긴다.
- **P2-1-R6 (반드시)** 청산가는 사용자가 거래소 화면에서 옮겨 적는 값만 쓴다. 앱이 거래소별 청산 공식을 계산하지 않는다 (P1 명세 4장 유지, 보완안 보류 1번).
- **P2-1-R7 (권장)** 화면 상단에 현재 포지션 요약(종목·방향·평단·수익률)과 마지막 갱신 시각을 항상 보여 주고, 분석을 시작할 때 대상 종목의 포지션(또는 "보유 없음")을 분석 시작 버튼 옆에 표시한다.
- **P2-1-R8 (반드시)** 분석 시작 시 **포지션 북을 읽어 `PositionContext`를 만들고 작업에 고정한다**. 이후 포지션 북이 바뀌어도 진행 중 작업은 영향받지 않는다 (스냅샷 불변 원칙과 같음).
- **P2-1-R9 (반드시)** 포지션 북의 `updatedAt`이 24시간보다 오래됐으면 분석 시작 화면과 결과에 `보유 정보가 N시간 전 기준` 경고를 표시한다. 차단하지는 않는다.
- **P2-1-R10 (반드시)** 대상 종목과 같은 `instrumentId`인데 `marketType`이 다른 포지션(예: BTC 현물을 들고 BTC 무기한을 분석)은 그 분석에 쓰지 않고, 결과에 `다른 시장 보유 있음: <종목·시장>` 한 줄만 표시한다. 이 한 줄은 코드가 만들며 모델에는 보내지 않는다.

## 2. 행동 집합 확장 (P2-2)

### 2.1 행동

| 값 | 의미 | 필요한 포지션 상태 |
|---|---|---|
| `ENTER_LONG` | 신규 롱/매수 진입 | 없음 |
| `ENTER_SHORT` | 신규 숏 진입 (`perpetual`만) | 없음 |
| `NO_TRADE` | 거래하지 않음 | 없음 |
| `HOLD` | 유지 (손절·목표 조정 가능) | 있음 |
| `ADD` | 같은 방향으로 추가 진입 | 있음 |
| `REDUCE` | 일부 청산. `sizeFraction`: 0.25·0.5·0.75 | 있음 |
| `EXIT` | 전량 청산 | 있음 |

- **P2-2-R1 (반드시)** 포지션이 있으면 `ENTER_*`·`NO_TRADE`를 쓸 수 없고, 없으면 `HOLD`·`ADD`·`REDUCE`·`EXIT`를 쓸 수 없다 (`V-POS-STATE`, 3.1절).
- **P2-2-R2 (반드시)** 포지션 방향의 **반대 방향 진입(리버설)은 한 번의 판정으로 하지 않는다.** 방향이 뒤집혔다고 판단하면 `EXIT`를 내고, 청산 후 새로 분석을 실행하면 포지션 없음 상태로 진입 여부를 본다. 결과에 이 안내 문구를 표시한다.
- **P2-2-R3 (반드시)** `bias`는 그대로 유지한다. 포지션이 있어도 `bias`(시장 방향)와 `action`(내 포지션에 할 일)은 분리한다. 예: 롱 보유 + `BEARISH` + `EXIT`.
- **P2-2-R4 (반드시)** 스키마 버전을 올린다: `proposal/3`, `decision/3`, 리포트 스키마 필드 추가. 이전 버전 작업·리포트는 읽기만 지원한다.
- **P2-2-R5 (반드시)** `TradeProposal`에 추가하는 필드:

```yaml
positionRef: UUID | null          # 사용한 포지션 id. 포지션 없음이면 null
sizeFraction: 0.25 | 0.5 | 0.75 | null   # REDUCE에서 필수, 그 외 null (EXIT는 전량)
stopLoss / targets                # HOLD·ADD: 갱신 값 (null이면 기존 값 유지)
```

  모델은 **수량을 제안하지 않는다.** 수량은 3.3절에서 코드가 계산한다.
- **P2-2-R6 (반드시)** `forced_direction` 모드는 포지션을 쓰지 않는 시뮬레이션이다. 포지션이 있어도 컨텍스트를 만들지 않고 결과에 `포지션 무시 시뮬레이션` 표시를 단다 (D23).
- **P2-2-R7 (반드시)** 최종 의사결정자는 P0 2장 그대로다: algorithm=PM, scalp=ACE. PM은 `HOLD`·`ADD`·`REDUCE`·`EXIT`도 승인·수정·기각할 수 있고, 기각이면 `HOLD`(포지션 있음) 또는 `NO_TRADE`(없음)로 처리한다.

### 2.2 화면 표기 조합

| 상태 | `action` | 표기 |
|---|---|---|
| 없음 | `ENTER_LONG` / `ENTER_SHORT` | 롱 진입 / 숏 진입 |
| 없음 | `NO_TRADE` + `bias` | 거래 없음 · 강세 전망 등 (P0 3.2) |
| 있음 | `HOLD` | 유지 |
| 있음 | `ADD` | 추가 진입 검토 |
| 있음 | `REDUCE` | 일부 청산 검토 (N%) |
| 있음 | `EXIT` | 전량 청산 검토 |

## 3. 결정론적 규칙 (P2-3)

P0 명세 3.6절 규칙은 그대로 적용하고, 포지션이 있을 때 다음을 추가한다. 위반 시 처리는 일반 모드에서 `DOWNGRADED → HOLD`(포지션 있음)이며, 강등해도 `bias`는 유지한다. `V-POS-STATE`만 `SCHEMA_ERROR`(재시도 대상)다.

### 3.1 규칙 표

| 코드 | 규칙 | 위반 시 |
|---|---|---|
| `V-POS-STATE` | 포지션 유무와 행동이 2.1절 표와 맞음, `positionRef`가 컨텍스트의 id와 같음, `REDUCE`면 `sizeFraction` 필수 | `SCHEMA_ERROR` |
| `V-POS-STOP-DIR` | `HOLD`·`ADD`의 (갱신된) 손절이 현재가 기준으로 올바른 쪽: 롱은 `stopLoss < 현재가`, 숏은 `stopLoss > 현재가`. 손절이 이미 현재가를 넘어섰으면 유지 불가 | `DOWNGRADED` → `EXIT`가 아니라 `HOLD` + 경고 `STOP_ALREADY_HIT`(화면에 강한 경고) |
| `V-STOP-WIDEN` | 기존 손절보다 **손실 방향으로 넓히는** 갱신 금지 (롱: 새 손절 < 기존 손절 금지, 숏: 반대) | 갱신 값을 무시하고 기존 손절 유지, 경고 |
| `V-POS-LIQ-BUFFER` | `liquidationPrice`가 입력돼 있으면 손절 거리 ≤ 0.5 × 현재가~청산가 거리 (P1 4.2 `V-LIQ-BUFFER`의 실측 버전. 이 경우 단순 계산 버전 대신 이 규칙을 쓴다) | `ADD` 차단 → `HOLD`. `HOLD`는 경고 |
| `V-POS-LIQ-NEAR` | 현재가~청산가 거리 < 2 × ATR(14): 위험 근접 | `ADD` 차단, 화면에 `청산가 근접` 경고. 행동은 모델 판단을 따른다 |
| `V-RISK-BUDGET` | `ADD`·`ENTER_*`의 제안 수량 > 0 이어야 함 (3.3절). 남은 리스크 예산이 0 이하면 `ADD` 금지 | `ADD` → `HOLD`, 사유 `RISK_BUDGET_FULL` |
| `V-EXIT-CONSISTENCY` | `EXIT`·`REDUCE`는 손절·목표 갱신이 무의미하므로 `stopLoss`·`targets`는 무시 | 무시 (경고 없음) |

- **P2-3-R1 (반드시)** 위 규칙은 프롬프트가 아니라 코드로 적용한다 (P0-3-R2).
- **P2-3-R2 (반드시)** 강등 결과가 `HOLD`여도 화면은 "규칙에 의해 모델 제안이 조정됨"과 위반 코드를 표시한다. 조용히 `HOLD`로 바꾸지 않는다.
- **P2-3-R3 (반드시)** 데이터 품질이 `INSUFFICIENT_DATA`이면 포지션이 있어도 모델 호출 없이 `INSUFFICIENT_DATA`다 (P0 D5). 이 결과의 화면에는 "포지션은 그대로이며 판정이 없음"을 표시하고 `HOLD` 등으로 보이게 하지 않는다.

### 3.2 파생 값 (코드 계산)

`PositionContext.derived`:

```yaml
unrealizedPnlPercent: number      # 롱: (현재가/평단 − 1), 숏: (평단/현재가 − 1)에 준하는 단순 % (레버리지 미반영 값과 반영 값 둘 다)
rMultiple: number | null          # 손절이 있으면 (현재 손익) / (평단~손절 거리). 손절 없음이면 null
stopDistancePercent: number | null
liquidationDistancePercent: number | null   # liquidationPrice 입력 시
positionWeightPercent: number | null        # (수량 × 현재가) / 해당 통화 총 자산, 총 자산 없으면 null
openRiskPercent: number | null              # 현재 손절까지 갔을 때 손실 / 총 자산
```

현재가는 스냅샷의 기준 가격(무기한: mark 우선, 없으면 last)이다. 추정 시세(`estimated`)로는 계산하지 않고 P0-4-R3대로 판정 자체를 막는다.

### 3.3 수량 제안 (리스크 예산)

```text
riskBudget      = equity[통화] × riskPerTradePercent / 100
existingRisk    = openRisk (기존 포지션이 손절까지 갈 때의 손실, 손절 없으면 "미정")
addableRisk     = max(0, riskBudget − existingRisk)
suggestedQty(ENTER_*) = riskBudget   / |진입 기준가 − stopLoss|
suggestedQty(ADD)     = addableRisk  / |진입 기준가 − stopLoss|
```

- **P2-3-R4 (반드시)** `suggestedQuantity`는 코드가 계산하고 모델은 값을 모른다. 결과에는 가정과 함께 표시한다: `총 자산 대비 손실 한도 N% 기준 · 수수료·슬리피지·펀딩비 미반영 · 참고용`.
- **P2-3-R5 (반드시)** 기존 포지션에 손절이 없으면 `existingRisk`를 알 수 없으므로 `ADD`의 수량 제안은 내지 않고 경고 `NO_STOP_ON_POSITION`을 표시한다. `HOLD`·`EXIT`·`REDUCE` 판정에는 영향이 없다.
- **P2-3-R6 (권장)** `perpetual`에서 `suggestedQuantity × 기준가 / leverage`(필요 증거금)가 총 자산의 50%를 넘으면 경고 `MARGIN_HEAVY`.
- 스캘핑 20x 등 레버리지가 높은 제안이 `V-LIQ-BUFFER`(P1 4.2)로 자주 강등될 수 있다. 이는 의도된 동작이다.

## 4. 모델에 보내는 포지션 정보 (P2-4)

### 4.1 역할별 입력

| 역할 | 포지션 정보 |
|---|---|
| TARO, DIANA, NOVA, VIBE | **없음** |
| BULL, BEAR | **없음** |
| BLITZ (scalp) | 있음 |
| GUARD (scalp) | 있음 |
| ACE | 있음 |
| RISKY, SAFE, NEUTRAL | 있음 |
| PM | 있음 |

- **P2-4-R1 (반드시)** 분석가 4명과 강세·약세 토론은 포지션을 보지 못한다 (D18). 보유 여부가 시장 분석과 토론의 방향을 물들이는 앵커링을 막고, 브리핑을 포지션과 무관한 재사용 가능한 자료로 남긴다. 그래서 호출 수는 P0 8장과 같다.
- **P2-4-R2 (반드시)** 모델 입력에는 **비율·상대값만** 넣는다: `side`, `leverage`, `marginMode`, `unrealizedPnlPercent`, `rMultiple`, `stopDistancePercent`, `liquidationDistancePercent`, `positionWeightPercent`, 현재 손절·목표 가격, 평단가, 포지션 보유 시간. **절대 금액·수량·총 자산·메모는 넣지 않는다.** 이 값들은 로컬 코드(수량 제안)에서만 쓴다.
- **P2-4-R3 (반드시)** 프롬프트에 다음을 명시한다: (a) 평단가와 현재 손익은 진입 근거가 아니다(매몰 비용 편향 금지), (b) `HOLD`·`ADD`·`REDUCE`·`EXIT` 중 하나를 고르고 `NO_TRADE`는 없다, (c) `ADD`는 근거가 신규 진입 기준을 만족할 때만, (d) 손절은 넓히지 않는다, (e) 수량은 제안하지 않는다.
- **P2-4-R4 (반드시)** `HOLD`를 "판단 회피"로 쓰지 못하게, `HOLD` 제안도 `evidenceRefs` 최소 개수(P1 10.2 `V-EVIDENCE-REF`)와 `invalidationConditions`(유지 판단을 뒤집을 조건)를 요구한다.
- **P2-4-R5 (반드시)** 포지션 정보는 신뢰 입력이지만(사용자가 넣음) 프롬프트에서는 뉴스 등 불신 블록과 분리된 별도 데이터 블록으로 전달한다.
- 사용자가 알아야 할 사실: 비율 정보라도 `claude` CLI를 통해 Anthropic으로 전송된다 (P0 6장 데이터 흐름 표에 행 추가). 가이드에 명시한다 (P2-6-R5).

### 4.2 `/floor` 경로

- **P2-4-R6 (반드시)** `/floor` 세션(하위 에이전트)은 `.floor/positions.json`을 직접 읽지 못한다(`floor-guard` 훅이 `.floor/` 읽기를 차단). 공통 코어 명령(`next`)이 돌려주는 역할별 입력에 4.1절 규칙대로 투영된 포지션 정보가 들어간다.

## 6. 화면·리포트 문구 (P2-6)

- **P2-6-R1 (반드시)** 톤은 **판정형 + 항상 고지** (D19): 표기는 `EXIT · 전량 청산 검토`처럼 판정과 근거를 쓰고, "지금 팔아라"식 지시문을 쓰지 않는다.
- **P2-6-R2 (반드시)** 판정 패널과 리포트에 다음 고지를 고정 표시한다: `자동 분석 결과이며 투자 자문이 아닙니다. 주문은 직접 실행하며 손실의 책임은 본인에게 있습니다.` 접기·숨기기 없음.
- **P2-6-R3 (반드시)** 포지션 인지 판정에는 사용한 포지션의 요약(방향·평단·수익률·손절·`positionAsOf`)을 함께 표시해 사용자가 입력 오류를 바로 알아챌 수 있게 한다. 일반 모드의 `NO_TRADE` 주석(BIAS_NOTE)은 포지션이 없다고 확인된 분석에서만 표시한다.
- **P2-6-R4 (반드시)** `REDUCE`·`EXIT`·`청산가 근접`·`손절 이미 도달` 표시는 정상(녹색) 색을 쓰지 않는다 (P0-3-T4 확장). `HOLD`는 중립색.
- **P2-6-R5 (반드시)** 가이드에 (a) 포지션 입력 방법, (b) 모델로 전송되는 정보(비율만, 금액·수량·메모 제외)와 로컬 저장 위치, (c) 수량 제안의 의미와 한계, (d) 이 앱은 주문하지 않는다는 점을 쓴다. 표지 문구 "분석 시뮬레이션"은 "분석 도구"로 정정한다.
- **P2-6-R6 (반드시)** "확실", "보장", "무조건" 같은 단정 표현을 화면·리포트 고정 문구에 쓰지 않는다. 확신도 표시 규칙(P0 3.5)은 그대로다.
