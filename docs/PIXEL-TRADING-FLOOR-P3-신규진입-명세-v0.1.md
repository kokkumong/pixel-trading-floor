## 0. 배경과 결정

사용자 결정(2026-10-01): 보유 포지션이 있어야 도움이 되는 구조는 부족하다. **새로 진입할 때** 도움이 되는 결과가 필요하다.

현재(P0~P2)는 포지션이 없을 때도 `ENTER_LONG`·`ENTER_SHORT`·`NO_TRADE`와 진입 구간·손절·목표가는 나온다. 그러나 신규 진입 사용자에게 다음이 비어 있다.

- **`NO_TRADE`가 막다른 길이다.** "지금은 거래 없음"에서 끝나고, 어떤 조건이면 들어갈지·언제 다시 볼지가 없다.
- **진입은 한 번에 한 구간뿐이다.** 눌림을 기다릴지, 돌파를 기다릴지, 나눠서 들어갈지에 대한 계획이 없다.
- **조건부 대안이 없다.** "지금은 롱이지만 이 가격 아래로 내려오면 숏 관점으로 전환"처럼 반대 시나리오가 없다.

이번 범위는 사용자가 고른 두 가지다: **진입 시나리오 카드**(P3-1·2)와 **분할 진입 계획**(P3-3). 다음은 이번 범위에서 제외한다: 진입 준비도 체크리스트, 종목 스캔·비교, 포지션 없는 리스크 사이징 입력 화면(총 자산·한도 입력은 P2 포지션 북 `account`가 이미 받는다. 포지션 0건이어도 쓸 수 있는지만 P3-3-R6에서 확인한다).

불변 조건 (P2 0장 그대로): 주문·거래소 API·자금 이동·가격 감시·알림 기능은 넣지 않는다. 모델 호출 수는 늘리지 않는다. 확신도는 LOW/MEDIUM/HIGH만 표시한다.

### 0.1 용어

| 용어 | 뜻 |
|---|---|
| 시나리오(`Scenario`) | 지금 진입 신호가 아니라 **조건이 충족되면** 진입하는 계획 1건. 방향·트리거·진입 구간·손절·목표·무효화·재확인 시점을 가진다 |
| 트리거 | 시나리오가 활성화되는 가격 조건 (눌림 `PULLBACK` 또는 돌파 `BREAKOUT`). 사람이 읽는 설명용이며 앱이 가격을 감시하지 않는다 |
| 분할 진입(`tranches`) | 하나의 진입 구간을 2~3개 가격·비중으로 나눈 계획. 공통 손절 1개 |
| 신규 진입 분석 | 포지션 컨텍스트가 없는 분석(보유 없음 또는 `forced_direction`이 아닌 일반 모드) |

### 0.2 P0·P2와 달라지는 점 요약

| 항목 | P0·P2 | P3 |
|---|---|---|
| `NO_TRADE` 결과 | 사유(`reasonCodes`)만 | + 재진입 조건이 있는 시나리오 1~2건, 재확인 시점 (2장) |
| `ENTER_*` 결과 | 진입 구간 1개 | + 조건부 대안 시나리오 (선택), 분할 진입 계획 (선택) |
| 스키마 | `proposal/3`, `decision/3` | `proposal/4`, `decision/4`, 리포트 필드 추가. 이전 버전은 읽기만 지원 |
| 포지션 보유 분석 | P2 행동 | **변경 없음.** 시나리오·분할 진입을 쓰지 않는다 |
| 모델 호출 수 | P0 8장 | **변경 없음** (제안서 작성자의 출력이 커질 뿐) |

## 1. 진입 시나리오 (P3-1)

### 1.1 스키마

`ProposalOutput`에 `scenarios` 배열을 추가한다 (`proposal/4`, 최대 2건).

```yaml
scenarios: Scenario[]            # 0~2건. 신규 진입 분석이 아니면 빈 배열
Scenario:
  role: PRIMARY | ALTERNATE      # PRIMARY: 이 판정에서 가장 가능성 높은 계획. 최대 1건
  side: LONG | SHORT             # SHORT는 perpetual만
  trigger:
    kind: PULLBACK | BREAKOUT    # PULLBACK: 가격이 level로 되돌아올 때, BREAKOUT: level을 돌파·이탈할 때
    level: number (> 0)          # 기준 가격
    timeframe: 15m | 1h | 4h | 1d
    confirmation: string (≤200)  # 예: "4시간봉 종가가 level 위에서 마감"
  entry: { type: limit | zone, min, max }   # market 불가 (조건부 진입이므로)
  stopLoss: number (> 0)
  targets: number 배열 (1~3개)
  leverage: 정수 | null          # perpetual이면 1~20, spot이면 null
  tranches: Tranche[] | null     # 3장. 없으면 null
  invalidationConditions: string 배열 (1~3개, 각 ≤300)
  recheckAfterMinutes: int       # 이 시간 뒤 다시 분석 권장
  evidenceRefs: string 배열 (1~5개)
  rationale: string (≤400)
```

- **P3-1-R1 (반드시)** 시나리오는 **조건부 계획**이다. 화면·리포트는 시나리오 카드에 `조건 미충족 — 아직 진입 신호가 아님` 문구를 고정 표시하고, 진입 신호 색(녹색·빨강)을 쓰지 않는다 (P0-3-T4 확장, 6장).
- **P3-1-R2 (반드시)** 시나리오는 `ENTER_*`·`NO_TRADE` 판정에만 붙는다. 다음 경우에는 `scenarios`를 비우고 쓰지 않는다: 포지션 컨텍스트가 있는 분석(P2 행동 사용), `forced_direction`(D23 취지: 반사실 시뮬레이션), `INSUFFICIENT_DATA`·`UNSUPPORTED_SYMBOL`·`SCHEMA_ERROR`.
- **P3-1-R3 (반드시)** `ENTER_*` 판정의 시나리오는 **대안**이다. 지금 진입안(기존 최상위 `entry`·`stopLoss`·`targets`)과 겹치지 않아야 한다. 예: `ENTER_LONG` + 더 깊은 눌림 재진입(`PULLBACK`), 또는 반대 방향 전환 조건(`SHORT` + `BREAKOUT` 이탈).
- **P3-1-R4 (반드시)** `PRIMARY` 시나리오의 방향은 판정의 `bias`와 같아야 한다 (`NEUTRAL`이면 어느 방향이든 가능). `ALTERNATE`는 반대 방향 가능.
- **P3-1-R5 (반드시)** 시나리오의 진입·손절·목표 기하와 손익비, 수량 제안, 위험 거리는 모델이 아니라 **코드**가 검사·계산한다 (4장, P3-4-R1). 모델은 수량을 제안하지 않는다.
- **P3-1-R6 (반드시)** 시나리오는 판정의 `validUntil`까지 유효하다. 만료 후 화면은 `만료됨`을 표시하고 재분석을 안내한다. `recheckAfterMinutes`는 `validForMinutes` 이하여야 한다.
- **P3-1-R7 (권장)** 시나리오의 `level`·진입 구간은 스냅샷의 지표·가격 구조에서 근거를 찾을 수 있어야 한다. `evidenceRefs`에 P1 10장 근거 검사를 적용한다 (시나리오마다 최소 1개, 경고만).

## 2. 관망(NO_TRADE)의 후속 안내 (P3-2)

- **P3-2-R1 (반드시)** 모델이 낸 `NO_TRADE`(사유 `NO_EDGE` 등)에는 `PRIMARY` 시나리오 1건 이상을 요구한다. 없으면 경고 `NO_WAIT_PLAN`을 결과에 표시하고(차단·재시도 없음), 화면은 `재진입 조건이 제시되지 않음`을 표시한다.
- **P3-2-R2 (반드시)** 규칙 엔진이 `ENTER_*`를 `NO_TRADE`로 **강등**한 경우(`DOWNGRADED`), 모델이 쓴 시나리오는 4장 규칙을 통과한 것만 남긴다. 강등 사유가 가격·방향 기하(`V-DIR-*`)이면 시나리오도 같은 오류를 가질 가능성이 높으므로 전부 재검사하고, 결과는 `규칙에 의해 모델 제안이 조정됨`(P2-3-R2)과 함께 표시한다.
- **P3-2-R3 (반드시)** `NO_TRADE`의 화면 표기는 P0 3.2절 그대로(`거래 없음 · 강세 전망` 등)이고, 시나리오 카드는 그 아래에 둔다. `거래 없음`이 `관망 = 안전`으로 읽히지 않게 `재확인 시점`을 카드 헤더에 표시한다.
- **P3-2-R4 (반드시)** 데이터 부족·지원 안 되는 종목 등 판정 자체가 없는 결과에는 시나리오를 만들지 않는다.

## 3. 분할 진입 (P3-3)

### 3.1 스키마

```yaml
tranches: Tranche[] | null       # 2~3건. 최상위 entry 또는 시나리오 entry가 zone일 때만
Tranche:
  price: number (> 0)            # 이 가격에 지정가로 진입
  weight: number                 # 비중. 모든 tranche의 합 = 1 (±0.001), 각 0.1~0.8
```

`ProposalOutput`의 최상위(지금 진입안)와 각 `Scenario`가 모두 `tranches`를 가질 수 있다.

### 3.2 계산 (코드)

```text
avgEntry = Σ (weight_i × price_i)
Q        = riskBudget / |avgEntry − stopLoss|         # riskBudget은 P2 3.3절과 같음
qty_i    = Q × weight_i                               # 코인은 소수 6자리, 주식은 1주 단위 내림
```

- **P3-3-R1 (반드시)** 분할 진입을 하더라도 **전부 체결된 뒤 손절까지 갔을 때 손실이 리스크 예산 이하**여야 한다. 그래서 수량은 모델이 아니라 가중 평균 진입가 기준으로 코드가 계산한다 (D30). 분할을 이유로 총 위험을 늘리지 않는다.
- **P3-3-R2 (반드시)** 분할 가격은 진입 구간 안에서 **불리한 방향으로 단계적**이어야 한다: 롱은 `price_1 > price_2 > price_3`, 숏은 `price_1 < price_2 < price_3`. 모든 가격은 `[entry.min, entry.max]` 안이고 손절의 올바른 쪽이다.
- **P3-3-R3 (반드시)** `tranches`가 있으면 수량 제안은 단일 수량이 아니라 **tranche별 가격·비중·수량·누적 수량** 표로 표시하고, 합계 수량·평균 진입가·전부 체결 시 손절 손실 금액·필요 증거금(`perpetual`)을 함께 보여 준다. 가정 문구는 P2-3-R4와 같다.
- **P3-3-R4 (반드시)** `scalp` 모드에서는 분할 진입을 쓰지 않는다 (`tranches = null`로 강제, D29). 20배 레버리지에서 불리한 방향 분할은 청산 거리 규칙(`V-LIQ-BUFFER`)과 자주 충돌한다. `algorithm` 모드에서만 쓴다.
- **P3-3-R5 (반드시)** 위험 거리 규칙 `V-LIQ-BUFFER`(P1 4.2)는 `perpetual` 분할 진입에서 **가중 평균 진입가**를 기준 진입가로 계산한다.
- **P3-3-R6 (반드시)** 대상 종목 통화의 총 자산이 없으면(`NO_EQUITY`) 수량은 생략하고 가격·비중만 표시한다. 포지션이 0건이어도 `account.equity`가 입력돼 있으면 수량을 계산해야 한다 (P2-1-R4 확인 항목, P3-3-T4).
- **P3-3-R7 (반드시)** 분할 계획 표시에 다음 문구를 고정한다: `1차 체결 후 무효화 조건에 해당하면 남은 분할은 진입하지 않는다.` 앱은 주문을 내지 않으므로 사람이 직접 실행한다는 점도 함께 표시한다.

## 4. 결정론적 규칙 (P3-4)

P0 3.6절·P1 4.2절·P2 3.1절 규칙은 그대로 적용한다. 다음을 추가한다. **시나리오·분할 규칙 위반은 판정을 강등하지 않고 해당 시나리오(또는 `tranches`)만 제거**하고 경고를 남긴다 (D31). 시나리오는 보조 정보이기 때문이다. 판정 자체(`action`)는 기존 규칙으로만 결정된다.

| 코드 | 규칙 | 위반 시 |
|---|---|---|
| `V-SCN-SHAPE` | 시나리오 수 ≤ 2, `PRIMARY` ≤ 1, `entry.type`은 `limit`·`zone`, `limit`이면 min = max, `zone`이면 min < max, 목표 1~3개, `SHORT`는 `perpetual`만, `recheckAfterMinutes ≤ validForMinutes` | 해당 시나리오 제거, 경고 `SCN_DROPPED` |
| `V-SCN-DIR` | 롱: `stopLoss < entry.min ≤ entry.max < targets[i]`. 숏: `targets[i] < entry.min ≤ entry.max < stopLoss` (P0 `V-DIR-*`와 같음) | 해당 시나리오 제거 |
| `V-SCN-TRIGGER` | 현재가(P2 3.2절 기준가) 기준: 롱 `PULLBACK`은 `level < 현재가`이고 `level ∈ [entry.min, entry.max]`, 롱 `BREAKOUT`은 `level > 현재가`이고 `level ≤ entry.min`. 숏은 반대 (`PULLBACK`: `level > 현재가`, `BREAKOUT`: `level < 현재가` 이탈) | 해당 시나리오 제거 |
| `V-SCN-DISTANCE` | `|level − 현재가| ≤ 5 × ATR(14)` (시나리오 `timeframe` 기준). 너무 먼 조건은 쓸모가 없다 | 해당 시나리오 제거. 임계값은 실측 전 값 |
| `V-SCN-BIAS` | `PRIMARY`의 방향이 `bias`와 일치 (`NEUTRAL`이면 무검사, P3-1-R4) | 해당 시나리오 제거 |
| `V-SCN-LEVERAGE` | `V-LEVERAGE-CAP`(≤ 20, spot이면 null)과 `V-LIQ-BUFFER`(P1 4.2)를 시나리오 진입가·손절로 계산 | 해당 시나리오 제거 |
| `V-SCN-DUP` | `ENTER_*` 판정의 시나리오가 지금 진입안과 같은 방향·겹치는 구간(구간 겹침 > 50%) | 해당 시나리오 제거 |
| `V-TRANCHE-SUM` | 2~3건, 각 weight 0.1~0.8, 합 1 (±0.001) | 해당 `tranches`만 제거 (단일 진입 유지), 경고 `TRANCHE_DROPPED` |
| `V-TRANCHE-ORDER` | P3-3-R2: 구간 안, 손절의 올바른 쪽, 불리한 방향으로 단계적 | `tranches` 제거 |
| `V-TRANCHE-SPREAD` | 인접 tranche 가격 간격 ≥ 0.2 × ATR(14). 간격이 너무 좁으면 분할 의미가 없다 | `tranches` 제거. 임계값은 실측 전 값 |
| `V-TRANCHE-MODE` | `scalp`·`forced_direction`·`entry.type`이 `zone`이 아닌 경우 `tranches = null` | `tranches` 제거 (경고 없음, 강제 정규화) |

- **P3-4-R1 (반드시)** 위 규칙·손익비·수량·위험 거리는 프롬프트가 아니라 코드로 적용한다 (P0-3-R2).
- **P3-4-R2 (반드시)** 코드는 시나리오마다 파생 값을 계산해 저장한다: `rewardRisk`(첫 목표까지 보상 ÷ 진입 불리한 쪽 가격~손절 위험, P2 3.3절과 같은 기준가), `sizing`(P2 3.3절, 총 자산 있을 때), `risk`(`perpetual` 위험 거리), `tranchePlan`(3.2절 계산). `rewardRisk < 1.5`면 경고 `LOW_REWARD_RISK`를 표시한다 (제거하지 않음, 임계값은 실측 전 값).
- **P3-4-R3 (반드시)** 제거된 시나리오와 사유 코드를 `decision.entryPlan.dropped`에 기록하고 화면에 `N개 시나리오가 규칙에 의해 제외됨`을 표시한다. 조용히 사라지지 않는다 (P2-3-R2 취지).
- **P3-4-R4 (반드시)** 이 규칙들은 `/floor` 경로와 브라우저 경로가 같은 코어(`next / submit / finalize`)에서 동일하게 적용한다 (P1-5-R1).

## 5. 모델 입력·프롬프트·호출 수 (P3-5)

- **P3-5-R1 (반드시)** 시나리오는 **제안서 작성자**가 쓴다: algorithm = ACE(PM이 승인·수정 가능), scalp = BLITZ(ACE가 결정). 분석가·강세/약세 토론·위험 토론 역할의 입력과 출력은 바꾸지 않는다. **호출 수는 P0 8장과 같다.**
- **P3-5-R2 (반드시)** 제안서 작성자의 프롬프트에 다음을 명시한다: (a) 신규 진입 분석이면 `NO_TRADE`일 때 `PRIMARY` 시나리오를 반드시 쓴다, (b) 시나리오는 스냅샷의 가격 구조·지표에서 근거를 찾은 가격만 쓴다, (c) 수량·금액은 제안하지 않는다, (d) `scalp`는 `tranches`를 쓰지 않는다, (e) 시나리오는 "조건이 충족되면"이지 "지금 진입"이 아니다.
- **P3-5-R3 (반드시)** PM이 제안서를 수정할 수 있는 필드에 `scenarios`·`tranches`를 포함한다. 수정은 `modifiedFields`에 기록한다 (P0 2.3절).
- **P3-5-R4 (반드시)** 제안서 출력이 커지므로 토큰·시간 상한(P0 8장)이 깨지지 않는지 측정한다. 상한 조정은 측정 후 `[구현 시 결정]`이며, 호출 수는 늘리지 않는다.
- **P3-5-R5 (반드시)** 시나리오 텍스트(`confirmation`·`invalidationConditions`·`rationale`)는 모델 출력이며 신뢰 입력이 아니다. 화면은 텍스트로만 렌더하고 HTML로 해석하지 않는다 (기존 UI 원칙 유지).

## 6. 화면·리포트 (P3-6)

- **P3-6-R1 (반드시)** 판정 패널에 `진입 시나리오` 영역을 둔다. 카드 1장 = 시나리오 1건:
  `[롱·눌림] 조건 4h 종가 > 92,400 유지 → 진입 구간 · 손절 · 목표 · 손익비 · 수량(분할 표) · 무효화 조건 · 재확인 N시간 뒤`.
  카드 상단에 `조건 미충족 — 아직 진입 신호가 아님`(P3-1-R1)을 고정 표시한다.
- **P3-6-R2 (반드시)** 시나리오 카드는 진입 신호 색(녹색·빨강)을 쓰지 않는다. 방향은 텍스트·아이콘으로만 구분하고 색은 중립으로 한다. `V-SCN` 제거 알림과 `LOW_REWARD_RISK`는 경고색이다.
- **P3-6-R3 (반드시)** 분할 진입은 3.3 R3 표로 표시하고, 마지막에 `전부 체결 시 손절 손실 ≤ 총 자산의 N%`를 보여 준다.
- **P3-6-R4 (반드시)** 리포트 JSON(`reports/*.json`)이 원본이고 `.md`는 JSON에서 생성한다 (P1-6). Markdown에 `## 진입 시나리오` 절을 추가한다. LAN 응답·`all.zip`·`project.zip`은 시나리오의 금액·수량(`sizing`·`tranchePlan`의 수량)을 `[masked]`로 처리한다 (P2-5-R3 확장).
- **P3-6-R5 (반드시)** 고정 고지(P2-6-R2)와 단정 표현 금지(P2-6-R6)는 시나리오 카드에도 그대로 적용한다. "이 가격에 사라"가 아니라 "이 조건이 충족되면 진입 후보"로 쓴다.
- **P3-6-R6 (반드시)** 가이드에 (a) 시나리오 카드 읽는 법(조건부 계획, 앱이 가격을 감시하지 않음), (b) 분할 진입과 수량 계산 방식, (c) `NO_TRADE`는 안전 신호가 아니라는 점, (d) 총 자산을 입력해야 수량이 나온다는 점을 쓴다.

## 7. 검증 항목

- **P3-1-T1** 롱 `PULLBACK` 시나리오가 `level ≥ 현재가`이거나 구간 밖이면 `V-SCN-TRIGGER`로 해당 시나리오만 제거되고 판정은 그대로다.
- **P3-1-T2** `forced_direction`·포지션 보유 분석·`INSUFFICIENT_DATA`는 `scenarios`가 비어 있고 화면에 카드가 없다.
- **P3-1-T3** `ENTER_LONG` 판정에서 지금 진입안과 구간이 50% 넘게 겹치는 롱 시나리오는 `V-SCN-DUP`으로 제거된다.
- **P3-1-T4** `bias = BULLISH`인데 `PRIMARY`가 숏이면 `V-SCN-BIAS`로 제거된다. `NEUTRAL`이면 통과한다.
- **P3-1-T5** 시나리오 카드가 녹색·빨강 진입 색 없이 렌더되고 `조건 미충족` 문구가 있다. 판정 `validUntil` 이후에는 `만료됨`이 표시된다.
- **P3-2-T1** `NO_TRADE`에 `PRIMARY`가 없으면 `NO_WAIT_PLAN` 경고가 표시되고 재시도·차단은 없다.
- **P3-2-T2** `V-DIR-LONG` 위반으로 강등된 `NO_TRADE`는 시나리오를 재검사하고 통과한 것만 보여 주며 `규칙에 의해 모델 제안이 조정됨`을 함께 표시한다.
- **P3-2-T3** `INSUFFICIENT_DATA` 결과에는 시나리오가 없고 `HOLD`·`관망 안전` 류 문구가 없다.
- **P3-3-T1** 총 자산 1,000 USDT·한도 1%·`zone` 100~96 롱, 손절 90, tranche (100, 0.5)·(98, 0.3)·(96, 0.2)이면 `avgEntry = 98.6`, `Q = 10 ÷ 8.6 = 1.162790`, tranche별 수량은 0.581395·0.348837·0.232558(내림)이다. 전부 체결 후 손절 손실은 10 USDT 이하다.
- **P3-3-T2** 롱에서 가격이 오름차순이거나(`V-TRANCHE-ORDER`), 비중 합이 1이 아니거나(`V-TRANCHE-SUM`), 간격이 0.2×ATR 미만이면(`V-TRANCHE-SPREAD`) `tranches`만 제거되고 단일 진입 수량이 남는다.
- **P3-3-T3** `scalp` 응답에 `tranches`가 있어도 정규화되어 null이 된다 (`V-TRANCHE-MODE`).
- **P3-3-T4** 포지션 북에 포지션 0건·`account.equity`만 있어도 `ENTER_LONG`·시나리오 수량이 계산된다. 총 자산이 없으면 수량은 생략되고 `NO_EQUITY`가 표시된다.
- **P3-3-T5** `perpetual` 분할 진입에서 `V-LIQ-BUFFER`가 가중 평균 진입가로 계산된다.
- **P3-4-T1** 시나리오·분할 규칙 위반은 `FinalDecision.action`을 바꾸지 않는다 (규칙 엔진 단위 테스트).
- **P3-4-T2** 제거된 시나리오는 `entryPlan.dropped`에 사유 코드와 함께 기록되고 화면에 개수가 표시된다.
- **P3-4-T3** `rewardRisk < 1.5`이면 `LOW_REWARD_RISK` 경고가 표시되고 시나리오는 유지된다.
- **P3-5-T1** 분석가 4명·BULL·BEAR·RISKY·SAFE·NEUTRAL 프롬프트가 P2와 동일하다 (프롬프트 캡처 검사). 호출 수 계획이 P0 8.3절과 같다.
- **P3-5-T2** 제안서 작성자 프롬프트에 `NO_TRADE`일 때 `PRIMARY` 시나리오 작성 규칙과 수량 비제안 규칙이 있고, 프롬프트 전체에 금액·수량·총 자산이 없다.
- **P3-5-T3** PM이 `scenarios`를 수정하면 `modifiedFields`에 기록된다.
- **P3-5-T4** 시나리오 텍스트의 HTML 태그가 화면에서 텍스트로만 렌더된다.
- **P3-6-T1** 리포트 JSON에서 생성한 Markdown에 `## 진입 시나리오` 절이 있고, 단정 표현이 없다.
- **P3-6-T2** LAN 응답·`all.zip`·`project.zip`에서 시나리오 수량이 `[masked]`다.
- **P3-6-T3** `proposal/3`·`decision/3` 이전 작업·리포트가 읽기 전용으로 계속 열린다 (시나리오 영역 없음).
- **P3-6-T4** 데모 fixture(알고리즘 `NO_TRADE` + 시나리오 2건, 알고리즘 `ENTER_LONG` + 3분할, 스캘핑 `ENTER_SHORT` + 대안 시나리오 1건)가 외부 요청 0건·모델 호출 0회로 완료되고 근거 검사 경고 0건이다.

### 9.1 남은 불확실성

1. 모델이 시나리오를 남발해 `NO_TRADE`를 회피하는 용도로 쓸 위험(P2의 `HOLD` 남용과 같다): `V-SCN-DISTANCE`·`evidenceRefs` 검사로 완화하되 측정 과제다.
2. `5 × ATR`·`0.2 × ATR`·`rewardRisk 1.5`·구간 겹침 50%는 실측 전 값이다. 첫 실전 분석 후 조정한다.
3. 시나리오 가격이 스냅샷의 어떤 지표(지지·저항 후보, 피벗 등)에서 나왔는지 구조화해 검증할 수 있을지는 구현 시 결정한다.
4. 제안서 출력 증가에 따른 토큰·시간 상한 영향은 측정 전이다 (P3-5-R4).
5. 사용자가 시나리오 가격 도달 여부를 직접 확인해야 하는 한계(앱은 감시하지 않는다). 재분석 안내와 `recheckAfterMinutes`로 완화한다.
