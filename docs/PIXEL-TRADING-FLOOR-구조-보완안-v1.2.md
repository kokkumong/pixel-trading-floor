## 1. 요약 결론

현재 설계는 `시장 데이터 → 역할별 분석 → 강·약 토론 → 1차 판정 → 리스크 심사 → 최종 결과 → 리포트 저장`이라는 큰 흐름은 이해하기 쉽다. 다만 호출 수, 모드별 최종 승인자, 데이터 기준 시각, 판정 스키마, 과거 판정 회고의 영향 범위, 외부 데이터 전송 설명 등이 명확하지 않다.

권장 방향은 다음 네 가지다.

1. 모든 모드가 하나의 공통 오케스트레이터와 명시적인 상태 머신을 사용한다.
2. 모든 에이전트가 동일한 검증 완료 데이터 스냅샷을 입력으로 받는다.
3. 에이전트의 자연어 응답과 시스템의 최종 판정을 분리하고, 판정은 고정 스키마로 검증한다.
4. 화면과 리포트에서 데이터 출처·기준 시각·추정 여부·실행 모드·위험 수준을 명시한다.

## 2. 권장 목표 구조

```text
사용자 요청
  ↓
입력 정규화 및 지원 여부 확인
  ↓
데이터 수집 어댑터
  ↓
검증·정규화·시각 동기화
  ↓
불변 분석 스냅샷 생성
  ↓
모드별 오케스트레이터
  ├─ 알고리즘: 분석 4 → 토론 → ACE → 리스크 3 → PM
  ├─ 스캘핑: 분석 2 → BLITZ → GUARD → ACE 또는 PM
  └─ 공격: 강제 방향 시뮬레이션 전용 경로
  ↓
정형 출력 검증 및 위험 규칙 적용
  ↓
화면 표시 + 버전이 포함된 원자적 리포트 저장
```

각 단계는 입력, 출력, 실패 상태, 재시도 정책, 시간 제한을 가져야 한다. 화면은 이 상태를 그대로 표시하고 별도의 암묵적 상태를 만들지 않는다.

## 3. 구조 문제별 대안

### 3.1 에이전트 수와 AI 호출 수의 의미 분리

#### 문제

가이드는 전체 에이전트를 13명으로 소개하면서 알고리즘 모드도 13회 호출한다고 설명한다. 그러나 `토론 4턴`이 발언 네 번인지, BULL·BEAR 왕복 네 쌍인지에 따라 실제 호출 수가 달라진다.

#### 대안

- `agentCount`: 제품에 정의된 역할 수
- `activeAgentCount`: 해당 모드에서 실제 참여하는 역할 수
- `modelCallCount`: 실제 모델 프로세스/API 호출 수
- `debateRoundCount`: BULL·BEAR 왕복 횟수
- `debateMessageCount`: 토론 발언 수

토론 용어는 다음 중 하나로 고정한다.

- 권장안: `1라운드 = BULL 1회 + BEAR 1회`, `4라운드 = 8발언`
- 절약안: `4턴 = BULL/BEAR 교대 발언 4회`

비용 안내에는 예상 범위를 사용한다.

```text
예상 모델 호출: 13회
토론 설정: 교대 발언 4회
재시도 발생 시 호출 수가 증가할 수 있음
```

#### 완료 기준

- 실행 로그의 호출 수와 UI 표시가 일치한다.
- 문서의 호출 수 산식이 한 줄로 재현 가능하다.
- 실패 재시도와 사용자 취소가 호출 수에 포함되는지 명시한다.

### 3.2 모드별 최종 의사결정자 명시

#### 문제

알고리즘 모드는 PM 승인을 거치지만 스캘핑·공격 모드는 ACE에서 끝나는 것으로 표시된다. 제품 전체 소개의 `PM 최종 승인` 표현과 일치하지 않는다.

#### 대안

두 가지 설계가 가능하다.

1. 모든 모드에서 PM 승인
   - 장점: 책임 구조와 출력 형식이 통일된다.
   - 단점: 호출 비용과 지연이 증가한다.
2. 모드별 최종 책임자 분리
   - 알고리즘: PM
   - 스캘핑: ACE
   - 공격: ACE가 생성하지만 `시뮬레이션 결과`로만 표기
   - 장점: 현재 호출 수를 유지할 수 있다.
   - 단점: 사용자가 모드별 결과의 권위를 혼동할 수 있다.

권장안은 2번이다. 대신 모든 결과에 다음을 의무적으로 넣는다.

```yaml
mode: algorithm | scalp | forced_direction
final_decision_maker: PM | ACE
risk_reviewed: true | false
forced_direction: true | false
```

#### 완료 기준

- 결과 화면과 리포트에 최종 의사결정자가 표시된다.
- PM 미참여 결과에 `PM 승인`이라는 문구가 나타나지 않는다.
- 공격 모드 결과를 일반 판정과 시각적으로 구분한다.

### 3.3 데이터 스냅샷 단일화

#### 문제

여러 에이전트가 서로 다른 시점 또는 서로 다른 출처의 데이터를 보면 토론의 전제가 달라진다.

#### 대안

분석 시작 시 한 번만 데이터 수집 단계를 실행하고 `AnalysisSnapshot`을 만든다. 모든 에이전트는 이 객체를 읽기 전용으로 공유한다.

권장 최소 스키마:

```yaml
snapshotId: UUID
symbolInput: 사용자 원문
instrumentId: 정규화된 내부 식별자
market: 거래소·시장·계약 종류
quoteCurrency: KRW | USD | USDT
requestedAt: ISO-8601
collectedAt: ISO-8601
sources:
  - provider: 문자열
    endpointType: price | candle | news | sentiment | fx | funding
    observedAt: ISO-8601
    fetchedAt: ISO-8601
    stale: boolean
    estimated: boolean
    status: ok | partial | failed
dataQuality:
  completeness: 0..1
  warnings: 문자열 배열
```

#### 정책

- 에이전트가 실행 중 외부 API를 직접 다시 조회하지 못하게 한다.
- 데이터 원천마다 최대 허용 경과 시간(TTL)을 정한다.
- 필수 데이터가 없으면 분석을 중단하고 `INSUFFICIENT_DATA`를 반환한다.
- 선택 데이터가 없으면 `PARTIAL_DATA`로 계속하되 결과에 경고를 남긴다.
- 화면의 15초 갱신 데이터와 분석에 고정된 스냅샷을 구분한다.

#### 완료 기준

- 한 분석에 참여한 모든 에이전트 로그에 같은 `snapshotId`가 기록된다.
- 리포트에서 분석 기준 시각과 현재 화면 시세를 구분할 수 있다.
- 오래된 데이터로 정상 판정이 생성되지 않는다.

### 3.4 데이터 출처 간 의미 정규화

#### 문제

현물, 무기한 선물, 환율 변환 가격, 추정 가격은 서로 직접 비교할 수 없다. 출처별 심볼과 거래 단위도 다를 수 있다.

#### 대안

내부에 `InstrumentRegistry`와 공급자별 어댑터를 둔다.

```yaml
instrumentId: KR:000660
displayName: SK하이닉스
assetClass: equity
primaryMarket: KRX
primaryCurrency: KRW
providerSymbols:
  yahoo: 000660.KS
  perpetualExchangeA: SKHYNIXUSDT
```

가격에는 항상 다음 태그를 붙인다.

- `spot` 또는 `perpetual`
- 실제값 또는 `estimated`
- 원 통화와 변환 통화
- 변환에 사용한 환율과 기준 시각
- 거래소 또는 공급자

#### 완료 기준

- 현물 가격을 선물 진입가로 오인할 수 없다.
- 서로 다른 통화의 가격을 환율 정보 없이 비교하지 않는다.
- 지원하지 않는 심볼은 유사 심볼로 임의 변환하지 않고 사용자에게 알린다.

### 3.5 실시간성의 등급화

#### 문제

모든 데이터가 같은 의미의 `실시간` 데이터는 아니다.

#### 대안

데이터 항목마다 신선도 등급을 정의한다.

| 등급 | 의미 | 예시 표시 |
|---|---|---|
| LIVE | 스트리밍 또는 매우 짧은 지연 | `LIVE · 3초 전` |
| NEAR_REALTIME | 짧은 주기 폴링 | `준실시간 · 24초 전` |
| DELAYED | 공급자 지연 가능 | `지연 가능 · 15분` |
| PERIODIC | 일·시간 단위 갱신 | `오늘 09:00 기준` |
| ESTIMATED | 다른 자료로 계산한 추정값 | `추정 · 직접 체결가 아님` |

UI에서 `실시간`이라는 단일 표현을 제거하고 이 등급과 기준 시각을 표시한다.

#### 완료 기준

- 모든 가격·뉴스·지표에 관측 시각 또는 갱신 시각이 있다.
- 소스가 시간을 제공하지 않으면 `시각 미확인`으로 표시한다.
- `ESTIMATED` 데이터는 다른 등급보다 우선해 표시된다.

### 3.6 판정 의미와 출력 스키마 통일

#### 문제

BUY/SELL/HOLD와 LONG/SHORT/PASS가 모드별로 혼용되며 대상 시장과 보유 기간이 불명확하다.

#### 대안

화면용 문구와 내부 판정을 분리한다. 내부 출력은 다음처럼 정규화한다.

```yaml
decision: ENTER_LONG | ENTER_SHORT | HOLD_EXISTING | NO_TRADE
instrumentId: 문자열
marketType: spot | perpetual
timeframe: 15m | 1h | 4h | 1d
expectedHoldingPeriod: 문자열
validUntil: ISO-8601
entry:
  type: market | limit | zone
  min: number | null
  max: number | null
stopLoss: number | null
targets: number 배열
confidence:
  score: 0..100
  calibrationVersion: 문자열
rationale: 문자열
invalidationConditions: 문자열 배열
warnings: 문자열 배열
```

`SELL`은 기존 보유분 청산인지 신규 숏 진입인지 분리해야 한다. `PASS`는 `NO_TRADE`로 통일하는 것이 명확하다.

#### 완료 기준

- 현물 종목에서 허용하지 않는 숏 판정이 생성되지 않는다.
- 진입가·손절가·목표가의 방향 관계가 자동 검증된다.
- 유효 시간이 지난 판정은 화면에서 만료 상태로 바뀐다.

### 3.7 과거 판정 회고의 영향 통제

#### 문제

과거 판정이 현재 판단에 어떻게 사용되는지 정의되어 있지 않아 자기확증, 사후편향, 프롬프트 팽창이 생길 수 있다.

#### 대안

과거 판정 회고를 두 단계로 분리한다.

1. 정량 평가
   - 당시 판정 시점 이후 미리 정한 평가 구간의 수익률
   - 최대 유리·불리 움직임
   - 손절·목표 도달 여부
2. 제한된 회고 입력
   - 최근 N건 또는 동일 시장 국면의 K건만 사용
   - 원문 전체 대신 정형 요약 사용
   - 현재 시점 이후의 정보가 과거 판단 평가에 섞이지 않도록 컷오프 적용

권장 정책은 과거 판정이 분석가들의 관측을 바꾸지 못하게 하고, ACE 또는 PM 단계에서만 보조 정보로 제공하는 것이다.

> v1.2 우선순위: 위 통제가 구현되기 전까지 회고는 기본 비활성화한다 (5장 P1 9번). 정량화된 회고의 효과를 P2에서 측정한 뒤 재활성화 여부를 정한다.

#### 완료 기준

- 회고 입력에 사용된 과거 리포트 ID가 기록된다.
- 평가 구간과 성공 판정 규칙이 사전에 고정된다.
- 회고 기능을 껐을 때도 분석 파이프라인이 정상 동작한다.

### 3.8 공격 모드의 제품적 격리

#### 문제

공격 모드는 근거 부족 상태에서도 방향을 강제로 선택하므로 일반 분석 결과로 오인될 수 있다.

#### 대안

- 내부 모드명을 `forced_direction`으로 지정한다.
- 첫 실행 때 별도 경고와 확인을 표시한다.
- 전체 화면에 `강제 방향 시뮬레이션` 배지를 유지한다.
- 일반 판정과 다른 색·아이콘·리포트 헤더를 사용한다.
- 기본 모드로 저장하거나 URL만으로 자동 실행하지 못하게 한다.
- 결과를 성과 통계에 포함할 경우 일반 모드와 분리 집계한다.

`확신도`는 강제 방향 여부와 독립적으로 계산해야 한다. 근거가 부족하면 방향을 선택하더라도 낮은 점수를 그대로 보존한다.

#### 완료 기준

- 공격 모드 결과를 캡처해도 시뮬레이션 표시가 함께 보인다.
- 일반 모드 리포트와 파일명 또는 메타데이터로 구별된다.
- 공격 모드의 결과가 기본 추천으로 재사용되지 않는다.

### 3.9 20배 레버리지 위험 모델 현실화

#### 문제

`20배는 약 5% 역행 시 청산`은 교육용 근사치일 뿐 실제 청산 가격이 아니다.

#### 대안

두 단계로 분리한다.

1. 거래소 미지정 상태
   - `단순 위험 거리`만 표시
   - 실제 청산가라는 표현 금지
2. 거래소·계약·마진 방식이 확인된 상태
   - 해당 거래소의 공식 계산 규칙 적용
   - 유지증거금, 수수료, 마크가격, 격리/교차 여부 반영

리스크 출력에는 다음을 포함한다.

```yaml
leverage: 20
marginMode: isolated | cross | unspecified
liquidationEstimateType: rough | exchange_formula
estimatedLiquidationPrice: number | null
assumptions: 문자열 배열
bufferToStopPercent: number | null
```

손절가가 예상 청산가보다 안전 방향에 있는지뿐 아니라, 변동성·슬리피지·갭 위험을 반영한 여유 폭도 검사한다.

> v1.2 우선순위: P1은 1단계(거래소 미지정 상태의 단순 위험 거리)만 구현한다. 2단계는 사용자가 거래소·마진 방식을 선택하는 기능이 생길 때까지 보류한다 (5장 보류 1번).

#### 완료 기준

- 거래소 미지정 시 정확한 청산가처럼 표시하지 않는다.
- 롱과 숏 계산을 각각 테스트한다.
- 수수료·유지증거금 설정 변경 시 결과가 예상 방향으로 변한다.

### 3.10 추정 시세의 사용 제한

#### 문제

탭비트 가격을 다른 거래소 평균으로 추정한다고 설명하지만, 이 값이 판정에 사용되는지 화면 표시용인지 불명확하다.

#### 대안

권장 정책은 추정 시세를 비교·전광판 표시용으로만 사용하고 진입가·손절가·청산 위험 계산의 기준에서는 제외하는 것이다.

> v1.2 우선순위: 이 권장 정책을 P0 명세에서 확정했다. 아래의 조건부 사용 경로는 채택하지 않으며, 추정값 산출 조건은 표시 품질 기준으로만 쓴다 (P1 명세 2장).

부득이하게 분석에 사용한다면 다음 조건을 모두 충족해야 한다.

- `estimated: true` 메타데이터
- 산출에 사용한 거래소 목록과 개별 가격
- 이상치 제거 방식
- 산출 시각
- 최대 허용 거래소 간 편차
- 편차 초과 시 분석 중단

#### 완료 기준

- 추정값이 실제값으로 표시되는 경로가 없다.
- 직접 시세가 복구되면 추정값보다 우선한다.
- 추정값만 존재할 때 레버리지 판정을 금지하거나 명시적 경고를 낸다.

### 3.11 브라우저와 `/floor`의 공통 실행 엔진화

#### 문제

브라우저 서버 호출과 Claude 세션 내 `/floor`가 서로 다른 코드 경로를 사용하면 결과와 안전장치가 달라질 수 있다.

#### 대안

다음 계층을 공유한다.

```text
공통 코어
  ├─ 입력 정규화
  ├─ 데이터 수집
  ├─ 프롬프트/역할 정의
  ├─ 오케스트레이션
  ├─ 출력 검증
  ├─ 위험 규칙
  └─ 리포트 생성

어댑터
  ├─ 웹 UI/서버
  └─ /floor 명령
```

두 실행 경로는 동일한 입력 스냅샷을 주입했을 때 같은 단계 수, 같은 검증 규칙, 같은 리포트 스키마를 만들어야 한다. 자연어 결과 자체의 완전 일치는 요구하지 않는다.

#### 완료 기준

- 공통 코어를 우회해 Claude를 호출하는 경로가 없다.
- 두 인터페이스의 회귀 테스트가 같은 검증 항목을 사용한다.
- 리포트에 실행 인터페이스와 코어 버전이 기록된다.

### 3.12 데모 모드와 실전 모드의 격리

#### 문제

데모 모드가 실제 데이터 수집·인증·모델 실패를 재현하지 않으므로 제품 정상성에 대한 잘못된 확신을 줄 수 있다.

#### 대안

- 데모 데이터는 별도 디렉터리와 명확한 fixture 버전을 사용한다.
- 데모 모드에서 외부 API와 Claude 호출을 구조적으로 차단한다.
- 리포트에 `demo: true`를 기록한다.
- 데모 리포트는 기본 목록에서 별도 분류한다.
- 데모 화면에는 항상 워터마크를 표시한다.
- 통합 진단 기능을 별도로 제공한다.

권장 진단 항목:

```text
Node 버전
Claude CLI 존재 여부
로그인 상태
API 키 사용 여부
필수 데이터 공급자 연결 상태
reports 쓰기 가능 여부
포트 사용 여부
```

#### 완료 기준

- 데모 모드가 실전 리포트로 분류되지 않는다.
- 데모 모드에서 외부 네트워크 요청이 발생하지 않는다.
- 진단 결과가 실패 원인을 단계별로 보여준다.

### 3.13 오케스트레이터 상태 머신과 실패 정책

#### 문제

문서는 정상 흐름만 설명하며 부분 실패, 응답 형식 오류, 시간 초과, 취소, 재시작을 정의하지 않는다.

#### 대안

분석 작업 상태를 명시적으로 관리한다.

```text
QUEUED
→ COLLECTING_DATA
→ VALIDATING_DATA
→ ANALYZING
→ DEBATING
→ RISK_REVIEW
→ FINAL_REVIEW
→ SAVING
→ COMPLETED

각 단계에서 → FAILED | CANCELLED | PARTIAL
```

각 모델 호출에는 다음 정책이 필요하다.

- 시간 제한
- 최대 재시도 횟수
- 재시도 가능한 오류 분류
- 지수 백오프
- 중복 호출 방지용 작업 ID
- 사용자 취소 전파
- 부분 결과 폐기 또는 보존 기준

#### 완료 기준

- 어느 단계에서 실패했는지 UI와 로그에서 확인된다.
- 동일 작업 재시도로 리포트가 중복 생성되지 않는다.
- 취소 후 백그라운드 모델 호출이 계속되지 않는다.

### 3.14 에이전트 출력과 시스템 규칙 분리

#### 문제

AI가 진입가·손절가·확신도 등을 자유 형식으로 생성하면 형식 오류와 수치 모순이 발생할 수 있다.

#### 대안

- 모델은 JSON 스키마에 맞는 제안서를 생성한다.
- 프로그램은 JSON을 파싱하고 타입·범위·방향 관계를 검증한다.
- 위험 한도와 금지 조건은 모델이 아니라 결정론적 코드가 적용한다.
- 자연어 브리핑은 표시용이며 승인 로직의 유일한 입력이 되지 않는다.

예시 규칙:

- 롱: `stopLoss < entry < target`
- 숏: `target < entry < stopLoss`
- 가격은 양수
- 확신도는 0~100
- 데이터 품질이 기준 미달이면 `NO_TRADE`
- 강제 방향 모드 외에는 근거 부족 시 `NO_TRADE` 허용

#### 완료 기준

- 잘못된 JSON, 누락 필드, 비정상 숫자를 테스트한다.
- 규칙 위반 결과가 UI에 정상 판정으로 표시되지 않는다.
- 모델이 위험 규칙을 무시해도 시스템이 차단한다.

### 3.15 리포트 저장 구조 개선

#### 문제

분 단위 파일명은 같은 종목을 같은 분에 여러 번 분석하면 충돌할 수 있다. 리포트 버전과 원본 데이터 추적 방식도 설명되지 않는다.

#### 대안

파일명은 초 단위 시각과 짧은 작업 ID를 포함한다.

```text
2026-07-30T15-28-43+09-00_KR-000660_a1b2c3d4.md
```

저장은 임시 파일에 먼저 기록하고 완료 후 원자적으로 이름을 바꾼다. 리포트 상단에는 다음 메타데이터를 둔다.

```yaml
reportSchemaVersion: 1
appVersion: 1.2.0
promptVersion: 문자열
jobId: UUID
snapshotId: UUID
mode: 문자열
demo: boolean
startedAt: ISO-8601
completedAt: ISO-8601
status: completed | partial | failed
```

#### 완료 기준

- 동시 실행으로 파일을 덮어쓰지 않는다.
- 저장 도중 종료되어도 완성된 리포트로 노출되지 않는다.
- 리포트만 보고 사용한 모드·데이터·프롬프트 버전을 추적할 수 있다.

### 3.16 외부 데이터 전송 설명 정정

#### 문제

가이드의 `수집한 데이터를 외부로 전송하지 않는다`는 표현은 외부 시장 API 및 Claude 사용 설명과 충돌한다.

#### 대안

문구를 데이터 흐름별로 나눈다.

권장 문안:

> 앱은 시장 데이터 제공자의 API와 뉴스 피드에서 데이터를 조회합니다. 실제 AI 분석 시 분석에 필요한 시장 데이터와 프롬프트가 Claude 서비스로 전송될 수 있습니다. 리포트는 기본적으로 사용자 PC에 저장되며, 앱 자체가 별도의 운영자 서버로 리포트를 업로드하지는 않습니다. 각 외부 서비스의 데이터 처리와 보존 정책은 해당 서비스 정책을 따릅니다.

별도의 데이터 흐름 표도 제공한다.

| 데이터 | 출발지 | 목적지 | 목적 | 저장 여부 |
|---|---|---|---|---|
| 티커 입력 | 사용자 브라우저 | 로컬 서버 | 분석 요청 | 로그 정책에 따름 |
| 시장 데이터 | 외부 공급자 | 로컬 서버 | 분석 자료 | 스냅샷 정책에 따름 |
| 프롬프트·분석 자료 | 로컬 서버 | Claude | AI 분석 | 서비스 정책에 따름 |
| 최종 리포트 | 로컬 서버 | 로컬 디스크 | 열람·다운로드 | 저장됨 |

#### 완료 기준

- 개인정보·외부 전송 안내가 실제 네트워크 흐름과 일치한다.
- 데모 모드와 실전 모드의 외부 통신 차이를 설명한다.
- 소스 코드의 네트워크 목적지 목록과 문서가 일치한다.

## 4. 공통 비기능 요구사항

### 4.1 관찰 가능성

각 분석 작업에는 `jobId`를 부여하고 다음을 기록한다.

- 단계 시작·종료 시각
- 사용한 데이터 스냅샷 ID
- 에이전트와 모델 식별자
- 호출 성공·실패·재시도 횟수
- 토큰 또는 사용량 정보가 제공되는 경우 해당 값
- 출력 스키마 검증 결과
- 최종 상태와 리포트 경로

민감한 인증 정보, 전체 환경변수, 인증 토큰은 로그에 기록하지 않는다.

### 4.2 재현 가능성

모델 결과의 완전 재현은 어렵더라도 다음은 고정할 수 있어야 한다.

- 입력 데이터 스냅샷
- 프롬프트 버전
- 모델 이름
- 호출 순서
- 시스템 위험 규칙 버전
- 리포트 스키마 버전

### 4.3 동시 실행 제어

- 사용자별 또는 서버별 최대 동시 작업 수를 설정한다.
- 같은 종목·같은 모드의 중복 실행 여부를 사용자에게 알린다.
- 서버 재시작 후 진행 중이던 작업을 실패 또는 복구 가능 상태로 정리한다.
- 보고서 파일명과 작업 ID로 충돌을 방지한다.

### 4.4 판정 품질 측정

단순 적중률만 사용하지 않는다. 모드별로 다음을 분리 집계한다.

- 방향 적중률
- 목표·손절 도달률
- 최대 유리 움직임과 최대 불리 움직임
- 기대 손익비
- `NO_TRADE` 비율
- 데이터 품질별 성능
- 일반 모드와 강제 방향 모드의 성능

AI 확신도는 실제 결과와 비교해 보정 정도를 측정해야 한다. 예를 들어 확신도 70인 판정들이 장기적으로 약 70% 수준의 정의된 성공 조건을 만족하는지 확인한다.

## 5. 우선순위

### 5.0 우선순위 구분 기준 (v1.2 개정)

v1.1은 P0를 "정의할 항목", P1을 "구현할 항목"으로 나눴지만, P0 항목에도 구현 요구사항이 포함되어 있고 14.2절 릴리스 게이트는 P0와 P1을 모두 요구한다. 따라서 두 등급의 차이는 "무엇을 먼저 하는가"이며, 기준을 다음과 같이 다시 정한다.

| 등급 | 기준 | 상세 명세 |
|---|---|---|
| P0 | 다른 모든 작업의 전제가 되는 **계약** (스키마, 스냅샷, 판정 권한, 보안 경계, 예산) | `PIXEL-TRADING-FLOOR-P0-명세` |
| P1 | P0 계약 위에서 **첫 실전 분석 전에** 갖출 기능과 검증 | `PIXEL-TRADING-FLOOR-P1-명세` |
| P2 | 실전 분석이 가능해진 뒤 **판정 품질을 검증**하는 체계 | 미작성 |

P0와 P1이 모두 완료되기 전에는 실전 분석 버전으로 배포하지 않는다 (14.2절).

### P0 — 다른 작업의 전제가 되는 계약

1. 호출·토론 단위 정의
2. 모드별 최종 의사결정자
3. 공통 판정 스키마
4. 데이터 스냅샷과 데이터 품질 정책 (추정 시세를 판정 기준에서 제외하는 정책 포함)
5. 공격 모드의 명시적 격리
6. 외부 데이터 전송 문구 정정
7. 로컬 전용 모드와 LAN 공유 모드의 보안 경계
8. 분석 한 건당 호출·토큰·시간·재시도 상한 (재시도 정책, 취소 시 하위 프로세스 종료 포함)
9. `/floor` 결과의 과도기 분류 (공통 코어 전환 전까지 간이 분석으로 구분)

### P1 — 첫 실전 분석 전에 갖출 항목

1. 작업 상태 머신, 부분 결과 처리, 서버 재시작 복구
2. 공급자별 심볼·시장 정규화 (추정 시세 표시 규칙 포함)

## 8. 실제 실행 가능성 검증 계획

문서에 적힌 설치 절차가 논리적으로 가능하다는 것과 실제 환경에서 재현된다는 것은 다르다. 실행 가능성은 새 Windows 환경을 기준으로 검증한다.

### 8.1 검증 환경 매트릭스

| 항목 | 최소 검증 조합 |
|---|---|
| 운영체제 | 지원 대상으로 명시한 Windows 버전 |
| Node.js | 최소 지원 버전, 현재 LTS |
| Claude Code | 지원 최소 버전, 최신 안정 버전 |
| 인증 방식 | Claude 구독 로그인, API 키 사용 환경 |
| 네트워크 | 정상, 느린 연결, 부분 차단, 오프라인 |
| 실행 방식 | `start-floor.cmd`, `npm start`, 직접 서버 실행, `/floor` |

### 8.2 종단 간 시나리오

1. 아무 개발 도구가 없는 환경에서 문서만 보고 설치한다.
2. 데모 모드가 외부 AI 호출 없이 동작하는지 확인한다.
3. 실전 모드에서 지원 티커별 분석을 실행한다.
4. 실제 모델 호출 수와 문서의 예상 호출 수를 비교한다.
5. 분석 도중 취소, 브라우저 종료, 서버 재시작을 시험한다.
6. 외부 데이터 공급자 하나씩 장애를 주입한다.
7. 생성된 리포트와 ZIP을 새 환경에서 열어본다.
8. 웹과 `/floor` 결과가 같은 스키마와 위험 규칙을 쓰는지 비교한다.

### 8.3 통과 기준

- 깨끗한 지원 환경에서 설치부터 리포트 생성까지 재현된다.
- 실패 시 `분석 실패`만 표시하지 않고 실패 단계와 사용자가 취할 조치를 알려준다.
- 지원 버전과 실제 동작 버전이 문서에 일치한다.
- 정상 종료와 비정상 종료 후 고아 프로세스가 남지 않는다.
- 중단된 작업이 완성 리포트로 노출되지 않는다.

## 9. 보안 위협 모델과 통제안

보안 검토는 실제 주문 기능 유무와 관계없이 필요하다. 이 앱은 로컬 웹 서버, 외부 네트워크, 사용자 입력, AI 출력, 파일 다운로드를 동시에 다루기 때문이다.

### 9.1 주요 공격면

| 공격면 | 주요 위험 | 권장 통제 |
|---|---|---|
| 로컬 HTTP 서버 | 같은 네트워크의 무단 접근 | 기본 `127.0.0.1` 바인딩, LAN 모드는 명시적 선택 |
| LAN 공유 | 리포트·프로젝트 노출 | 임시 접근 토큰, 만료, 화면 경고, 요청 로그 |
| 티커·모드 입력 | 명령 삽입, 경로 조작 | 허용 목록과 정규식 검증, 셸 문자열 결합 금지 |
| `/reports` | 경로 이동, 임의 파일 읽기 | 고정 루트와 정규화된 경로, 파일 ID 기반 조회 |
| `/reports/all.zip` | 민감 리포트 일괄 노출 | 로컬 전용 또는 인증, 크기 제한, 명시적 생성 |
| `/project.zip` | 인증정보·소스·설정 유출 | 기본 비활성화, 제외 목록, 생성 전 포함 파일 표시 |
| 뉴스·RSS | 프롬프트 인젝션 | 외부 텍스트를 불신 데이터로 태깅, 명령 해석 금지 |
| AI 응답 표시 | XSS와 악성 링크 | HTML 이스케이프, 안전한 Markdown 렌더링, URL 정책 |
| 외부 URL 요청 | SSRF와 과대 응답 | 공급자 도메인 허용 목록, 리디렉션 제한, 응답 크기 제한 |
| Claude 프로세스 | 권한 남용과 고아 프로세스 | 최소 권한, 인자 배열 실행, 취소 시 프로세스 트리 종료 |
| 로그·오류 화면 | 키·토큰·개인정보 노출 | 비밀값 마스킹, 환경변수 전체 출력 금지 |

### 9.2 로컬과 LAN 모드 분리

기본 실행은 로컬 컴퓨터에서만 접근 가능해야 한다.

```text
기본: 127.0.0.1:8000
선택적 LAN 공유: 0.0.0.0:8000 + 임시 토큰 + 명시적 경고
```

LAN 모드에서는 다음이 필요하다.

- 실행할 때마다 새 접근 토큰 발급
- 토큰 만료와 수동 폐기
- `/project.zip` 기본 차단
- 리포트 목록과 다운로드 접근 통제
- Origin/Host 검증
- 요청 횟수 제한

### 9.3 명령 실행 안전성

- `exec`, `spawn` 사용 시 셸을 거치지 않고 실행 파일과 인자를 배열로 전달한다.
- 티커, 모드, 파일명, 사용자 문장을 명령 문자열에 이어 붙이지 않는다.
- 사용자 입력으로 실행 파일 경로, 작업 디렉터리, 환경변수를 변경하지 못하게 한다.
- Claude 호출에 전달할 환경변수는 허용 목록 방식으로 구성한다.

### 9.4 외부 콘텐츠와 프롬프트 인젝션

뉴스·RSS·과거 리포트에는 `이전 지시를 무시하라`와 같은 문장이 포함될 수 있다. 이 텍스트는 지시가 아니라 분석 대상 데이터로만 처리해야 한다.

권장 통제:

- 시스템 지침과 외부 콘텐츠를 구조적으로 분리한다.
- 외부 콘텐츠 내부의 도구 호출·파일 접근·명령 실행 요구를 무시하도록 시스템 규칙을 둔다.
- 에이전트에게 필요한 데이터 필드만 전달한다.
- 기사 원문 전체보다 제목·출처·시각·제한된 길이의 요약을 사용한다.
- AI 응답만으로 코드 실행이나 파일 접근을 허용하지 않는다.

### 9.5 보안 통과 기준

- 경로 이동, 명령 삽입, XSS, SSRF 기본 테스트를 통과한다.
- ZIP 산출물에 인증정보와 불필요한 사용자 파일이 포함되지 않는다.
- 외부 뉴스 문장이 시스템 명령으로 실행되지 않는다.
- LAN 모드가 아닌 경우 다른 기기에서 서버에 접근할 수 없다.
- 로그와 오류 응답에서 비밀값이 발견되지 않는다.

## 10. 비용과 자원 사용 통제

모델 호출 비용 또는 구독 사용량은 정상 호출뿐 아니라 재시도, 중복 클릭, 동시 실행, 비정상 장문 응답으로 증가할 수 있다.

### 10.1 작업 예산

모드마다 다음 상한을 설정한다.

```yaml
maxModelCalls: 정수
maxRetriesPerStage: 정수
maxInputSize: 정수
maxOutputSize: 정수
maxDurationSeconds: 정수
maxConcurrentJobs: 정수
```

상한을 넘으면 추가 호출을 시작하지 않고 `BUDGET_EXCEEDED` 상태로 종료한다. 이미 생성된 부분 결과는 완성 판정과 구분해서 보존할 수 있다.

### 10.2 호출 중복 방지

- 분석 버튼 연속 클릭을 하나의 작업으로 합친다.
- 같은 요청의 재전송을 식별하는 idempotency key를 사용한다.
- 실행 중인 동일 종목·모드 작업이 있으면 사용자에게 알려준다.
- 사용자 취소 시 대기 중 호출과 실행 중 하위 프로세스를 모두 종료한다.

### 10.3 모델 라우팅

모든 역할에 같은 고비용 모델을 고정하지 않는다. 역할별 품질 요구를 측정한 뒤 모델을 배정한다.

- 데이터 정리와 형식 변환: 결정론적 코드 우선
- 단순 요약: 경량 모델 후보
- 논쟁 종합과 최종 판단: 상대적으로 강한 모델 후보
- 위험 한도 적용: 모델이 아니라 코드

모델 변경은 비용뿐 아니라 품질 회귀 테스트를 통과해야 한다.

### 10.4 비용 통과 기준

- 모드별 정상·최악 호출 수를 사전에 계산할 수 있다.
- 재시도 포함 최대 사용량을 넘지 않는다.
- 실행 전 예상 사용량, 실행 후 실제 호출 수를 확인할 수 있다.
- 취소된 작업에서 추가 호출이 계속되지 않는다.
- 모델별 품질과 사용량을 비교할 수 있다.

## 11. 에이전트 설계 품질 보완

### 11.1 독립 분석 단계

TARO, DIANA, NOVA, VIBE는 서로의 결론을 보기 전에 분석을 완료한다. 초기 단계에서 답을 공유하면 첫 번째 결론에 나머지가 동조하는 앵커링이 발생할 수 있다.

각 분석은 다음을 분리한다.

```yaml
observations: 직접 관찰한 데이터와 출처
interpretations: 관찰에 대한 해석
assumptions: 확인되지 않은 전제
counterScenario: 반대 방향 시나리오
changeTriggers: 판단이 바뀌는 조건
dataLimitations: 데이터 한계
```

### 11.2 토론 품질

BULL과 BEAR는 상대방의 가장 강한 근거를 먼저 요약한 뒤 반박하는 `steelman` 방식을 사용한다. 새로운 데이터가 없는 반복 발언은 근거 수를 늘리지 않은 것으로 처리한다.

토론 종료 조건은 단순 횟수 외에 다음을 고려한다.

- 새로운 근거가 더 이상 나오지 않음
- 핵심 쟁점이 명확히 정리됨
- 데이터 부족으로 결론 불가능
- 호출 예산 도달

### 11.3 ACE와 PM의 역할 구분

- ACE: 분석과 토론을 바탕으로 거래 제안서 작성
- 위험 규칙 엔진: 수치 관계와 금지 조건 검사
- PM: 충돌 해결, 위험 한도 내 승인·수정·기각

PM이 ACE의 답변을 다시 표현하는 역할에 그치지 않도록 승인 사유와 변경 필드를 정형화한다.

```yaml
pmDecision: APPROVE | MODIFY | REJECT
modifiedFields: 문자열 배열
reasonCodes: 문자열 배열
```

### 11.4 기준선과 제거 실험

다음 네 방식을 동일 데이터에서 비교한다.

1. 단순 기술 규칙
2. 단일 AI
3. 현재 멀티 에이전트
4. 보완된 멀티 에이전트

또한 에이전트를 하나씩 제거하는 ablation test로 각 역할의 실제 기여도를 측정한다. 성능 향상이 없고 비용만 늘리는 역할은 통합하거나 제거한다.

### 11.5 에이전트 설계 통과 기준

- 각 주장의 원천 데이터와 출처를 추적할 수 있다.
- 독립 분석 전 다른 에이전트 결론이 노출되지 않는다.
- 다수결이 아니라 근거 품질과 위험 규칙으로 최종 판정한다.
- 멀티 에이전트가 단일 모델 대비 어떤 지표를 개선하는지 제시한다.
- 역할 제거 실험으로 각 에이전트의 필요성을 설명할 수 있다.

## 12. 금융 데이터와 계산 정확성

기존 스냅샷·정규화 요구사항에 다음 금융 예외를 추가한다.

### 12.1 주식 데이터

- 거래소 시간대, 휴장일, 조기 폐장
- 장전·정규장·시간외 데이터 구분
- 주식 분할, 병합, 배당, 수정주가
- 거래정지와 가격 제한
- 동일 기업의 서로 다른 상장 시장 구분

### 12.2 선물·무기한 데이터

- 계약 승수와 가격 단위
- 마크 가격, 지수 가격, 최종 체결가 구분
- 펀딩비의 부호, 주기, 다음 지급 시각
- 격리·교차 마진 구분
- 거래소별 유지증거금 단계
- 최소 주문 단위와 가격 정밀도

### 12.3 캔들 무결성

- 중복·누락·역순 캔들 탐지
- 완성되지 않은 현재 캔들 표시
- 타임프레임 변환 시 경계 정렬
- 거래량 단위와 통화 명시
- 급격한 이상치가 복수 공급자에서 확인되는지 검사

### 12.4 계산 테스트

MA, RSI, MACD, ATR, 변동성, 손익비, 청산 추정 등은 고정된 입력과 예상 출력으로 단위 테스트한다. 외부 차트 도구 또는 독립 구현과 표본 비교해 오차 범위를 기록한다.

### 12.5 금융 정확성 통과 기준

- 시간대와 휴장일 때문에 잘못된 `MARKET OPEN`이 표시되지 않는다.
- 수정주가와 원시 가격의 용도가 섞이지 않는다.
- 미완성 캔들이 백테스트에서 완성 캔들처럼 사용되지 않는다.
- 거래소별 청산 계산 가정이 결과에 표시된다.
- 핵심 지표가 독립 기준값과 허용 오차 내에서 일치한다.

## 13. 백테스트·워크포워드·모의 운용

구조가 올바르다는 것과 판정이 유효하다는 것은 별개다. 판정 품질은 시간 순서를 보존한 별도 평가로 검증한다.

### 13.1 평가 데이터 분리

- 개발 구간: 프롬프트와 규칙 설계
- 검증 구간: 선택안 비교
- 최종 테스트 구간: 마지막 한 번의 평가
- 실시간 모의 구간: 배포 형태로 미래 데이터만 사용

동일한 테스트 구간을 반복 확인하며 프롬프트를 조정하면 테스트 데이터가 사실상 학습 데이터가 되므로 변경 이력을 기록한다.

### 13.2 미래 정보 누출 방지

- 분석 시점 이후 공개된 뉴스 금지
- 당시 이용 가능했던 캔들만 사용
- 미완성 캔들의 미래 종가 사용 금지
- 현재 시점에 보정된 데이터가 과거 시점에 존재했다고 가정하지 않기
- 과거 판정 회고도 당시 이용 가능했던 리포트만 사용

### 13.3 현실적 거래 조건

백테스트에 다음을 포함한다.

- 진입·청산 수수료
- 예상 슬리피지
- 펀딩비
- 지정가 미체결 가능성
- 가격 갭과 손절 초과 체결
- 거래소·시장 운영시간
- 동시 포지션과 자본 배분 한도

### 13.4 비교와 통계

- 단순 보유, 무작위 방향, 기술 규칙, 단일 AI와 비교한다.
- 종목·기간·시장 국면별 결과를 분리한다.
- 평균뿐 아니라 분산, 최대 낙폭, 표본 수를 표시한다.
- 여러 전략을 반복 시험한 뒤 가장 좋은 결과만 선택하는 다중검정 편향을 기록한다.
- 개선폭이 비용과 복잡성을 정당화하는지 평가한다.

### 13.5 실시간 모의 운용

코드 변경을 멈춘 고정 버전으로 일정 기간 모의 운용한다. 판정이 생성된 당시의 스냅샷과 결과를 수정 불가능한 형태로 남기고, 사후에 실제 가격 흐름과 비교한다.

### 13.6 품질 통과 기준

- 기준선보다 개선된 지표와 악화된 지표를 모두 공개한다.
- 거래 비용 적용 후에도 결과가 유지된다.
- 확신도 구간과 실제 성공률의 관계를 측정한다.
- 충분한 표본이 없으면 `검증 미완료`로 표시한다.
- 강제 방향 모드는 일반 분석 성과와 분리한다.

## 14. 테스트·릴리스·운영 기준

### 14.1 테스트 계층

1. 단위 테스트
   - 심볼 정규화, 지표 계산, 판정 규칙, 경로 검증
2. 통합 테스트
   - 데이터 어댑터, Claude 호출 래퍼, 리포트 저장
3. 종단 간 테스트
   - 입력부터 화면·리포트까지 전체 흐름
4. 실패 주입 테스트
   - API 시간 초과, 잘못된 JSON, 부분 데이터, 디스크 오류
5. 보안 테스트
   - 경로 이동, 명령 삽입, XSS, SSRF, ZIP 포함 파일
6. 장시간 테스트
   - 동시 실행, 메모리 누수, 고아 프로세스, 파일 충돌

외부 API와 모델을 직접 호출하지 않는 고정 fixture 테스트와 실제 샌드박스 호출 테스트를 분리한다.

### 14.2 릴리스 게이트

다음 중 하나라도 충족하지 못하면 실전 분석 버전으로 배포하지 않는다.

- P0와 P1 요구사항 완료
- 치명적·높음 등급 보안 문제 없음
- 지원 환경 종단 간 테스트 통과
- 핵심 금융 계산 단위 테스트 통과
- 호출·시간·재시도 상한 적용
- 데이터 출처와 기준 시각 표시
- 데모·추정·강제 방향 결과 구분
- 문서와 실제 네트워크·인증·저장 동작 일치

### 14.3 성숙도 단계

| 단계 | 의미 | 사용 범위 |
|---|---|---|
| M0 | 화면 데모 | UI 시연만 가능 |
| M1 | 실행 재현 | 지원 환경에서 분석 완료 가능 |
| M2 | 구조·보안 강화 | 실패와 입력을 안전하게 통제 |
| M3 | 품질 검증 | 기준선·백테스트·워크포워드 결과 확보 |
| M4 | 운영 검증 | 장기간 모의 운용과 회귀 관리 |

이 프로젝트는 수익을 보장하는 단계가 아니라 `어떤 조건에서 어느 정도 신뢰할 수 있는 분석 시뮬레이션인가`를 설명할 수 있는 단계까지를 목표로 한다.

## 15. 확장된 최종 승인 기준

구조 검토 승인 기준에 더해 다음을 만족해야 전체 개발 보완이 완료된 것으로 본다.

- 새 Windows 환경에서 문서만으로 설치·실행을 재현했는가?
- 로컬 서버·입력·파일·외부 콘텐츠의 주요 공격면을 차단했는가?
- 작업당 최대 호출·재시도·시간·동시 실행 수가 제한되는가?
- 취소 시 모든 하위 작업과 프로세스가 종료되는가?
- 분석가의 초기 판단이 서로 독립적인가?
- 각 주장에 검증 가능한 데이터 근거가 연결되는가?
- 에이전트 수 증가가 단일 모델보다 실제로 유리한가?
- 금융 지표와 청산 계산이 독립 기준값과 일치하는가?
- 미래 정보 누출 없이 백테스트와 워크포워드 평가를 수행했는가?
- 수수료·슬리피지·펀딩비를 반영했는가?
- 일정 기간의 실시간 모의 운용 기록이 있는가?
- 높은 확신도가 실제로 더 높은 성공률과 연결되는가?
- 주요 회귀·장애·보안 테스트가 자동화되어 있는가?

마지막 항목까지 통과하더라도 실제 투자 수익이나 안전한 레버리지 거래를 보장하지는 않는다. 이 승인 기준의 목적은 결과를 과신하지 않고, 시스템의 동작과 한계를 재현 가능하게 설명하는 데 있다.
